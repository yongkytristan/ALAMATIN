# Contributing to ALAMATIN

## Branches

- `feat/<short-description>` for product, model, data, or documentation work.
- `fix/<short-description>` for defect corrections.
- Use lowercase kebab-case, for example `feat/address-normalizer`.
- Do not commit directly to `main` after branch protection is enabled.

## Commits

Write imperative, scoped messages such as `docs: define dataset provenance`.
Do not combine unrelated changes. Never include secrets, personal data, or large
generated artifacts in commit history.

## Pull requests

1. Link one primary issue with `Closes #...` or `Refs #...`.
2. Explain the outcome, verification performed, privacy impact, and limitations.
3. Keep the change small enough for one coherent review. Split work that cannot
   be reviewed independently.
4. Obtain at least one approving reviewer before merge.
5. Resolve requested changes and ensure required checks pass.

Completion means acceptance criteria pass; writing code alone is not enough.
